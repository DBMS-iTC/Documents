== Introduction

=== Technology Area and Scope of Supporting Document

This Supporting Document (SD) defines Evaluation Activities (EAs) for the *{pp-module-name}* (DBMS_MOD_CRYPTO), version {pp-module-version}. The technology area addressed is Database Management Systems (DBMS) that implement cryptographic protections for data at rest and for cryptographic key management.

This SD provides Evaluation Activities that evaluators shall perform to determine whether a TOE satisfies the Security Functional Requirements (SFRs) specified in the DBMS Cryptographic Functions PP-Module. These activities complement the Evaluation Activities defined in the Supporting Document for the collaborative Protection Profile for Database Management Systems (cPP_DBMS SD), which remains applicable for all SFRs inherited from the Base PP.

The Evaluation Activities in this SD are derived from the Common Evaluation Methodology (CEM:2022) work units and are aligned with the framework defined in CC:2022 Part 4 for specifying objective, repeatable, and reproducible evaluation methods.

=== Structure of the Document

This Supporting Document is organized to mirror the structure of the PP-Module and follows the SFR class hierarchy defined in CC:2022 Part 2.

*Section 2: General Guidance for Evaluators* provides overarching guidance applicable across multiple SFRs, including:

* Relationship between this module and the Crypto Catalogue
* Handling selections and assignments in the ST
* Catalogue claims verification
* Evaluator coordination with the Crypto Catalogue evaluation activities

*Section 3: Assurance Activities Overview* describes:

* Mapping to Base PP SARs
* Documentation requirements

*Subsequent sections* define Evaluation Activities organized by SFR class:

* FCS: Cryptographic Support (DBMS Extensions)
* FDP: User Data Protection

Within each class section, Evaluation Activities are specified for each SFR, organized into:

* *TSS Activities*: Verification of the TOE Summary Specification
* *Guidance Activities*: Verification of operational and preparative guidance
* *Test Activities*: Independent functional testing procedures

=== Terminology

The following terms are used throughout this Supporting Document:

Evaluation Activity (EA)::
An activity derived from one or more CEM work units that specifies the actions evaluators shall perform to determine whether the TOE meets a specific SFR or SAR. Evaluation Activities are objective, repeatable, and produce determinate results.

TOE Summary Specification (TSS)::
The section of the Security Target that describes how the TOE Security Functionality (TSF) meets each Security Functional Requirement. Evaluators verify that the TSS provides sufficient detail to understand the security mechanisms implemented.

Guidance Documentation::
The set of documents provided by the developer that describe how to securely install, configure, and operate the TOE. This includes operational guides, preparative procedures, and configuration references for cryptographic key management.

Test::
A procedure performed by the evaluator to verify that the TSF behaves as specified. Tests include test objectives, test setup, test procedures, and expected results.

Selection::
An operation performed by the ST author to choose one or more items from a list provided in an SFR component. The evaluator verifies that selections are valid and that the TSS describes how the selected functionality is implemented.

Assignment::
An operation performed by the ST author to specify a value or set of values for a parameter in an SFR component. The evaluator verifies that assignments are appropriate and that the TSS describes how the assigned values are implemented.

Crypto Catalogue::
The *Specification of Functional Requirements for Cryptography* (CCDB-018) [<<Crypto_Catalog>>], the Common Criteria standard defining SFRs for cryptographic algorithm implementations. The DBMS Cryptographic Functions PP-Module invokes the Catalogue for all standard algorithm requirements and defers algorithm-level Evaluation Activities to the Catalogue.

DEK (Data Encryption Key)::
A symmetric cryptographic key used to encrypt and decrypt database user data. DEKs are generated by the TOE and stored only in wrapped (encrypted) form under the Master Encryption Key (MEK).

MEK (Master Encryption Key)::
The root cryptographic key in the DBMS key hierarchy. The MEK wraps DEKs. MEK lifecycle is governed by `FCS_CKM_EXT.1`.

BYOK (Bring Your Own Key)::
A key management model in which the customer supplies their own MEK to the TOE. BYOK is implemented via `FCS_CKM_EXT.1` (import selection) and `FDP_ITC_EXT.1` (trusted import channel).

== General Guidance for Evaluators

This section provides guidance applicable across multiple Evaluation Activities in this Supporting Document. Evaluators shall consider this guidance when performing any evaluation of a TOE claiming conformance to the DBMS Cryptographic Functions PP-Module.

=== Relationship to the Crypto Catalogue

==== What Is and Is Not Evaluated by This SD

The PP-Module invokes the *Specification of Functional Requirements for Cryptography* (CCDB-018) [<<Crypto_Catalog>>] for all standard cryptographic algorithm implementations. This SD does *not* define Evaluation Activities for:

* Algorithm correctness (e.g., Known Answer Tests, DRBG health tests)
* Signature generation and verification algorithm tests
* Hash function correctness tests
* Key derivation function tests

The evaluator shall apply the Assurance Activities defined *within* the Crypto Catalogue for all Catalogue components claimed in the ST. This SD provides Evaluation Activities *only* for the DBMS-specific extensions defined in the PP-Module:

* Key hierarchy management (DEK/MEK)
* Master Key import (BYOK) via a trusted channel
* Data-at-rest encryption strategy (Full Volume/TDE or Granular)

==== Required Catalogue Component Claims

Before conducting SFR-specific evaluation activities, the evaluator shall verify that the ST includes all required Catalogue component claims as specified in the PP-Module's Crypto Catalogue Claims appendix.

The evaluator shall examine the ST to confirm it claims, at minimum:

[cols="2,2,2",options="header"]
|===
| Purpose | Required Component | CCDB-018 Section

| Symmetric-key data encryption (DEK)
| `FCS_COP.1/SKC` and/or `FCS_COP.1/AEAD`
| §4.10 and/or §4.2

| Random Bit Generation (key generation)
| `FCS_RBG.1`
| §6.2

| Hashing (integrity, key wrap verification)
| `FCS_COP.1/Hash`
| §4.4

| Key Destruction (MEK/DEK lifecycle)
| `FCS_CKM.6`
| §3.7
|===

The evaluator shall additionally verify:

. When `FCS_CKM_EXT.1.1` selects "Imported from External Entity", the ST claims TLS channel components from the Functional Package for TLS v2.1 (`FCS_TLSC_EXT.1` or `FCS_TLSS_EXT.1`).
. When mutual authentication is selected in `FDP_ITC_EXT.1.2`, the ST claims an asymmetric signature component (e.g., `FCS_COP.1/SigGen`) for certificate-based authentication.
. All Catalogue component claims include the required assignments (key sizes, algorithm parameters, standards references) per CCDB-018 guidance notes.

The evaluator shall also verify that the guidance documents identify which Catalogue-defined algorithms are used for each cryptographic operation, and that the TOE's behaviour observed during testing is consistent with the claimed Catalogue components.

=== Handling Selections and Assignments

==== Evaluating SFRs with Selections

When an SFR includes a selection operation, the evaluator shall:

. Verify that the ST author selected one or more valid options from the selection list.
. Verify that selected options are consistent with the TOE's actual capabilities.
. Verify that the TSS describes how the selected functionality is implemented.
. Verify that guidance documentation describes how to configure and use the selected functionality.
. Perform tests that exercise the selected functionality.

Key selections in this PP-Module and their evaluation implications:

* `FCS_CKM_EXT.1.1`: "Generated Internally" vs. "Imported from External Entity" — determines whether MEK generation tests or MEK import/BYOK tests apply. Both selections require testing; the evaluator performs the tests applicable to the selected path.
* `FDP_DAR_EXT.1.1`: "Full Volume Encryption" vs. "Granular Data Encryption" — determines which storage inspection tests apply. Both selections require testing for the selected path.
* `FDP_ITC_EXT.1.2`: "Mutual Authentication" vs. "Server Authentication" — determines whether client certificate tests apply.

==== Evaluating SFRs with Assignments

When an SFR includes an assignment operation, the evaluator shall:

. Verify that the ST author provided appropriate values for the assignment.
. Verify that assigned values are consistent with the TOE's capabilities and the security problem definition.
. Verify that the TSS describes how the assigned values are implemented.
. Verify that assigned values are sufficiently specific to enable deterministic testing.

==== Verifying ST Author Made Valid Selections

The evaluator shall verify that selections are:

* *Valid*: The selected option appears in the SFR selection list.
* *Complete*: Required selections are made (no unresolved selections remain).
* *Consistent*: Selections across SFRs are mutually compatible.
* *Accurate*: Selected functionality is actually implemented by the TOE.

== FCS Class: Cryptographic Support (DBMS Extensions)

=== FCS_CKM.1/SKG Cryptographic Key Generation (Data Encryption Keys)

This SFR requires the TSF to generate Data Encryption Keys (DEKs) for database encryption using an approved symmetric key generation method. The key generation algorithm (via `FCS_RBG.1`) is defined by the Crypto Catalogue. This SD covers the DBMS-specific aspects: the use of DEKs within the key hierarchy and the protection of generated DEKs under the Master Encryption Key (MEK).

==== FCS_CKM.1/SKG Evaluation Activities

===== TSS Activities

The evaluator shall verify the TSS describes:

* The mechanism for generating Data Encryption Keys (DEKs), consistent with the selection made in `FCS_CKM.1.1/SKG` (random generation or key derivation).

* The supported DEK key sizes in bits, consistent with the assignment in `FCS_CKM.1.1/SKG` and the claimed `FCS_COP.1/SKC` or `FCS_COP.1/AEAD` parameters.

* The key hierarchy: how generated DEKs are immediately protected (wrapped) by the Master Encryption Key (MEK). The TSS shall explicitly state that DEKs are never stored in plaintext on persistent storage.

* When DEKs are generated (e.g., at tablespace creation, at column encryption enablement) and the conditions under which they may be regenerated or rotated.

* The source of randomness used for DEK generation, identifying the specific Catalogue RBG component (`FCS_RBG.1`) consumed.

*Application Note:* If the TSS states that DEK generation is performed by the platform or by an external component rather than the TOE itself, the evaluator shall verify this claim is consistent with the TOE boundary as described in the ST and that any platform-provided key generation meets the Catalogue requirements through appropriate environmental assumptions.

===== Guidance Activities

The evaluator shall verify the guidance describes:

* Any administrator-visible steps associated with DEK generation, such as enabling encryption on a tablespace, database, or column set.

* How to verify DEK generation has succeeded (e.g., via system views, status commands, or log entries).

* Any configuration parameters that affect DEK generation behaviour (e.g., key size selection, algorithm mode selection where multiple options are supported).

* A statement that DEKs are managed automatically by the TOE and that administrators should not attempt to access or export DEK material directly.

===== Test Activities

*Test 1: DEK Generation and Wrapping Verification*

. Step: Configure the TOE with a known Master Encryption Key (MEK_1) per the administrator guidance.
. Step: Enable database encryption on a new tablespace, database, or column set, triggering DEK generation.
. Step: Stop the DBMS service to flush memory caches.
. Step: Using a binary editor or appropriate inspection tool, examine the persistent storage location where the key store or encrypted data resides.
. Step: Search for any known plaintext representation of the generated DEK (e.g., using a key handle or identifier from a system view to correlate).

Expected result: The DEK is present only in encrypted (wrapped) form in persistent storage. No plaintext DEK material is discoverable.

*Test 2: DEK Key Size Consistency*

. Step: Examine system views, status commands, or audit logs that report the encryption algorithm and key size for active encrypted objects.
. Step: Verify the reported key size matches the assignment made in `FCS_CKM.1.1/SKG` and the corresponding `FCS_COP.1/SKC` or `FCS_COP.1/AEAD` claims.

Expected result: All active DEKs use the key size(s) specified in the ST. No objects use key sizes not claimed in the ST.

=== FCS_CKM_EXT.1 Cryptographic Key Management (Master Keys)

This SFR governs the full lifecycle of the Master Encryption Key (MEK) — the root key in the DBMS key hierarchy. It covers internal generation and external import (BYOK) of the MEK, along with protection and destruction requirements.

==== FCS_CKM_EXT.1 Evaluation Activities

===== TSS Activities

The evaluator shall verify the TSS describes:

* Which option is selected in `FCS_CKM_EXT.1.1` ("Generated Internally" or "Imported from External Entity") and the rationale for that selection.

*If "Generated Internally" is selected, additionally verify the TSS describes:*

* The algorithm and randomness source used for MEK generation (referencing the applicable Catalogue RBG component, `FCS_RBG.1`).
* The storage location of the generated MEK (e.g., software keystore/wallet, filesystem-protected keyfile, platform key store integration).
* The protection mechanism applied to the stored MEK (e.g., password-based encryption of the keystore, filesystem ACLs, OS keyring or HSM integration).
* How the TOE ensures the MEK storage location is accessible only to authorized roles.

*If "Imported from External Entity" is selected, additionally verify the TSS describes:*

* The type of external entity from which the MEK is imported (e.g., Key Management Service, HSM, cloud key vault).
* The protocol used for the import channel (referencing `FDP_ITC_EXT.1`).
* The authentication requirements for the import operation (consistent with the selection in `FDP_ITC_EXT.1.2`).
* How the imported MEK is stored and protected within the TOE boundary after import.

*For all selections, additionally verify the TSS describes:*

* How the MEK is protected against disclosure and modification while in use (in-memory protection).
* The MEK destruction procedure, including the method by which MEK material is overwritten or otherwise rendered unrecoverable (consistent with `FCS_CKM.6` Catalogue claims) and the effect of MEK destruction on data encrypted under DEKs that were protected by the destroyed MEK.

===== Guidance Activities

The evaluator shall verify the guidance describes:

* Step-by-step instructions for MEK generation (if "Generated Internally" is selected), including prerequisite configuration (e.g., keystore location), the command or procedure to generate the MEK, and how to verify generation succeeded.

* Step-by-step instructions for MEK import (if "Imported from External Entity" is selected), including prerequisites for establishing the connection to the external KMS (network access, certificate configuration), the command or procedure to initiate and complete the import, and how to verify the import succeeded and the MEK is active.

* The MEK rotation procedure, including the steps to generate or import a new MEK, how DEK re-wrapping occurs (automatically or requiring an administrator action), how to verify data remains accessible after rotation, and any operational impact or downtime considerations.

* The MEK destruction procedure, including the command or procedure to destroy the MEK, a clear warning that MEK destruction renders all data encrypted under dependent DEKs permanently inaccessible, and the method used for key material zeroization (consistent with the `FCS_CKM.6` claims).

* How to restrict access to the MEK storage location to authorized roles only.

===== Test Activities

*Test 1: Master Key Generation (Internal)*

Applicable when "Generated Internally" is selected in `FCS_CKM_EXT.1.1`.

. Step: Following the administrator guidance, configure the TOE keystore and generate a new MEK.
. Step: Verify the MEK artifact (keystore file or equivalent) is created at the location specified in the guidance and ST.
. Step: Using a standard unprivileged operating system account (not the database administrator or keystore owner), attempt to read the MEK artifact directly.
. Step: Inspect the structure of the MEK artifact using a binary or hex editor to verify it is not stored in plaintext.

Expected result: The unprivileged account is denied access to the MEK artifact. The artifact does not contain any recognizable plaintext key material.

---

*Test 2: Master Key Import (BYOK)*

Applicable when "Imported from External Entity" is selected in `FCS_CKM_EXT.1.1`.

. Step: Configure the TOE and an external KMS test instance per the administrator guidance.
. Step: Using a network traffic capture tool, monitor the connection between the TOE and KMS.
. Step: Initiate the MEK import operation from the TOE.
. Step: Examine the captured traffic and verify it uses the protocol claimed in `FDP_ITC_EXT.1` (e.g., TLS 1.3).
. Step: Verify the TOE reports a successful import (via system view, log, or status command).
. Step: Encrypt a small test dataset using the imported MEK.
. Step: Verify the test dataset is accessible (decrypt and read the data).

Expected result: The import channel uses the claimed protocol. The import succeeds and the imported MEK is functional for data encryption and decryption.

---

*Test 3: Master Key Rotation*

. Step: Configure the TOE with an initial MEK (MEK_1) and encrypt a test dataset.
. Step: Record the encrypted form of a DEK protected by MEK_1 (if observable via a system view or key store inspection tool).
. Step: Following the administrator guidance, perform a MEK rotation to MEK_2.
. Step: If the DEK wrapped form is observable, verify it has changed (now wrapped under MEK_2).
. Step: Verify the test dataset remains readable after rotation.
. Step: If supported by the TOE, attempt to revert to MEK_1 (which should no longer be active) and verify data remains accessible via MEK_2.

Expected result: DEKs are re-wrapped under MEK_2 after rotation. Data remains accessible. MEK_1 is no longer the active wrapping key.

---

*Test 4: Master Key Destruction*

. Step: Configure the TOE with a MEK and encrypt a test dataset. Note that the dataset is accessible (reads succeed).
. Step: Initiate MEK destruction per the administrator guidance.
. Step: Immediately after destruction, attempt to read the test dataset.
. Step: Inspect the persistent MEK storage location (keystore file or equivalent) to verify the MEK material has been removed or overwritten.

Expected result: The test dataset is no longer accessible after MEK destruction. The persistent storage location no longer contains the MEK material in any recoverable form.

---

=== FCS_CKM.6 Cryptographic Key Destruction (Catalogue Reference)

This SFR is satisfied by a claim against `FCS_CKM.6` (CCDB-018 §3.7, Timing and Event of Cryptographic Key Destruction) as mandated in the PP-Module's Catalogue Claims appendix. The primary Evaluation Activities for key destruction algorithm correctness are defined within the Crypto Catalogue and shall be applied by the evaluator. This SD provides supplementary activities specific to the DBMS context.

==== FCS_CKM.6 Evaluation Activities

===== TSS Activities

The evaluator shall verify the TSS describes:

* That `FCS_CKM.6` is the key destruction method, consistent with the Catalogue claim.
* The specific destruction method selected (e.g., single overwrite with zeros, overwrite with a pseudo-random pattern) and confirmation that it applies to both MEK and DEK material.
* When key destruction occurs (e.g., explicit administrator command, expiry-triggered destruction, key rotation completion) and whether any keys are excluded from destruction requirements.

===== Guidance Activities

The evaluator shall verify the guidance describes:

* The key destruction commands or procedures available to authorized administrators.
* A clear statement of the irreversibility of key destruction and the impact on encrypted data.

===== Test Activities

*Note:* Detailed zeroization testing is performed as part of the Crypto Catalogue evaluation activities for `FCS_CKM.6`. The following supplementary test verifies DBMS-specific destruction behaviour.

*Test 1: Key Material Absence Post-Destruction*

. Step: Create and activate a MEK and record any observable identifier (key ID, fingerprint).
. Step: Initiate key destruction per the administrator guidance.
. Step: After destruction, query any system views or key management interfaces that list active or archived keys.
. Step: Inspect the persistent key store location for the destroyed key's identifier or material.

Expected result: The destroyed key no longer appears in system views or key management interfaces. The key store location does not contain the key material in any recognizable form.

== FDP Class: User Data Protection

=== FDP_DAR_EXT.1 Data-at-Rest Encryption Strategy

This SFR governs how the TOE applies encryption to persistent database storage. The ST author must select either Full Volume Encryption or Granular Data Encryption. The cryptographic algorithms used are defined by Catalogue claims (`FCS_COP.1/SKC` or `FCS_COP.1/AEAD`).

*Note:* When this PP-Module is used as a mandatory component of the DBMS Cloud Module PP-Configuration, the ST author may alternatively select "Leverage Platform Encryption" via the Cloud Module's FDP_DAR_EXT.1.1. In that case, no data-at-rest cryptographic testing is required for this module, as encryption is provided entirely by the Operational Environment. Refer to the DBMS Cloud Module SD for the applicable evaluation activities.

==== FDP_DAR_EXT.1 Evaluation Activities

===== TSS Activities

The evaluator shall verify the TSS describes:

* Which strategy is selected in `FDP_DAR_EXT.1.1`: Full Volume Encryption or Granular Data Encryption.

*If "Full Volume Encryption" is selected, additionally verify the TSS:*

* Defines the scope of encryption — which storage objects are encrypted. At minimum, the TSS shall address: data files, transaction/redo log files, undo/rollback segment files, and temporary tablespace or temp files. If any of these categories are not encrypted, the TSS shall explicitly state this and provide a security rationale.
* Identifies the encryption algorithm and mode (consistent with `FCS_COP.1/SKC` or `FCS_COP.1/AEAD` claims).
* Describes how encryption is applied transparently to the DBMS (i.e., applications do not need modification to benefit from encryption).

*If "Granular Data Encryption" is selected, additionally verify the TSS:*

* Defines the granularity level (column-level, row-level, cell-level, or a combination).
* Identifies which encryption modes are supported (e.g., deterministic, randomized/probabilistic) and the security implications of each:
** *Deterministic* encryption produces the same ciphertext for the same plaintext and key, enabling equality searches and indexing but leaking frequency information.
** *Randomized (probabilistic)* encryption produces different ciphertext for the same plaintext, providing stronger confidentiality but preventing sorting, range queries, and indexing on encrypted values.
* Describes how encrypted columns or data elements interact with database indexing, query processing, and backup/restore operations.
* Identifies any data types or storage formats that are excluded from granular encryption and provides rationale.

*For all selections, additionally verify the TSS:*

* Identifies the encryption algorithm, key size, and mode of operation, confirming consistency with the claimed `FCS_COP.1/SKC` and/or `FCS_COP.1/AEAD` Catalogue components.

===== Guidance Activities

The evaluator shall verify the guidance describes:

* Step-by-step instructions for enabling encryption (Full Volume or Granular) appropriate to the selection made in the ST.

* *For Full Volume Encryption:*
** Instructions for enabling encryption on a new database and on an existing unencrypted database.
** Guidance on how to verify the encryption status of individual storage objects (e.g., via system views, status queries, or utility commands).
** Backup and restore procedures for encrypted databases, including key availability requirements during restore.
** Guidance on the encryption status of temporary storage, redo logs, and archived log files.

* *For Granular Data Encryption:*
** Instructions for encrypting individual columns or data elements.
** Guidance on selecting the appropriate encryption mode (deterministic vs. randomized) for different use cases.
** Instructions for querying and indexing encrypted data, noting any limitations.
** Guidance on key management for column-level encryption (e.g., whether separate keys are used per column or a shared key is used).

* Performance considerations and tuning recommendations related to encryption.

* How to disable or re-encrypt data and the impact on key management.

===== Test Activities

*Test 1: Full Volume Encryption — Storage Inspection*

Applicable when "Full Volume Encryption" is selected. The evaluator requires low-level access to storage files (binary editor, raw disk access, or equivalent).

. Step: Create a test database or tablespace and insert rows containing distinctive, easily searchable plaintext strings (e.g., `EVALUATOR_TEST_STRING_12345`).
. Step: Ensure encryption is enabled for that database or tablespace.
. Step: Stop the DBMS service to flush all in-memory buffers and caches to disk.
. Step: Using a binary editor or equivalent tool, scan the raw storage files for the known plaintext strings.

Expected result: The plaintext strings are not found in the storage files. File contents appear as high-entropy (encrypted) data.

---

*Test 2: Full Volume Encryption — Scope Coverage*

Applicable when "Full Volume Encryption" is selected.

. Step: Execute queries that generate redo/transaction log entries and temporary sort operations containing the same distinctive plaintext strings used in Test 1.
. Step: Stop the DBMS service.
. Step: Inspect the raw files for redo logs, undo logs, and temporary tablespace/temp files.

Expected result: Verify that the scope of encryption coverage in practice is consistent with what the TSS claims. If the TSS states redo logs are not encrypted, verify this and note it as consistent with the ST. If the TSS states redo logs are encrypted, verify the plaintext is not present.

---

*Test 3: Granular Encryption — Column Encryption Inspection*

Applicable when "Granular Data Encryption" is selected.

. Step: Create a test table containing at least one encrypted column and at least one unencrypted column.
. Step: Insert rows with known plaintext values in both column types.
. Step: Stop the DBMS service.
. Step: Inspect the raw storage files using a binary editor.

Expected result: Known plaintext values are present in the storage files for unencrypted columns. Known plaintext values are *not* present for encrypted columns — those storage locations contain ciphertext (high-entropy data).

---

*Test 4: Granular Encryption — Deterministic vs. Randomized Mode Behaviour*

Applicable when "Granular Data Encryption" is selected and the TOE supports both deterministic and randomized encryption modes.

_Procedure for Deterministic Encryption:_

. Step: Create a column with deterministic encryption enabled. Insert the same plaintext value in two separate rows.
. Step: Inspect the stored ciphertext values for the two rows (via a system view, binary inspection, or a raw export).
. Step: Attempt to create an index on the deterministically encrypted column.
. Step: Perform an equality search (`WHERE col = 'known_value'`) on the column.

Expected result: Both rows storing the same plaintext produce the same ciphertext. Index creation and equality searches succeed.

_Procedure for Randomized Encryption:_

. Step: Create a column with randomized encryption enabled. Insert the same plaintext value in two separate rows.
. Step: Inspect the stored ciphertext values.
. Step: Attempt to create a B-tree or standard index on the randomized column.

Expected result: The two rows storing the same plaintext produce different ciphertext values. Index creation fails or is rejected per the TSS description.

---

=== FDP_ITC_EXT.1 Trusted Channel for Key Import

This SFR governs the trusted channel used to import the Master Encryption Key from an external Key Management System (KMS) in BYOK scenarios. The channel protocol (TLS) is evaluated using the Functional Package for TLS v2.1 [<<TLS_FP>>]. This SD covers the DBMS-specific channel properties: authentication behaviour, key material protection in transit, and failure handling.

*Application Note:* The evaluator shall also apply TLS Evaluation Activities from the Functional Package for TLS v2.1 for the `FCS_TLSC_EXT.1` or `FCS_TLSS_EXT.1` components claimed in the ST. The activities below are supplementary and focus on the DBMS-to-KMS key import use case specifically.

==== FDP_ITC_EXT.1 Evaluation Activities

===== TSS Activities

The evaluator shall verify the TSS describes:

* The specific protocol used for the trusted channel (e.g., TLS 1.3, TLS 1.2 with specific ciphersuites) and confirms consistency with the TLS components claimed from the Functional Package for TLS v2.1.

* The authentication mode selected in `FDP_ITC_EXT.1.2`:
** If *Mutual Authentication* is selected: describes the certificate infrastructure used (TOE client certificate, KMS server certificate), the certificate validation procedure, and where client certificates are stored within the TOE.
** If *Server Authentication* is selected: describes how the TOE validates the KMS server certificate (trusted CA, certificate pinning, or equivalent) and how the TOE prevents connection to an unauthenticated KMS.

* How the TOE handles channel establishment failures, including rejection of KMS connections presenting untrusted or expired certificates, handling of TLS negotiation failures (e.g., protocol version mismatch, cipher suite mismatch), and behavior when the KMS is unreachable (timeout, fail-closed vs. fail-open consideration).

* That key material transmitted over the channel is protected by the TLS layer and is never transmitted in plaintext.

===== Guidance Activities

The evaluator shall verify the guidance describes:

* Prerequisites for establishing the trusted channel, including certificate requirements (CA certificates to be trusted, client certificate generation and installation if mutual authentication is used) and network access requirements (ports, firewall rules).

* Instructions for configuring the TOE to connect to the external KMS, including KMS endpoint configuration (hostname/IP, port) and certificate or credential configuration for the channel.

* The procedure for rotating or updating certificates used in the channel.

* How to test channel connectivity before performing a key import, and how to diagnose channel establishment failures.

* The TOE's behavior when the KMS is unavailable (e.g., whether cached key material allows continued operation or whether the TOE fails to start or denies new connections).

===== Test Activities

*Test 1: Successful Channel Establishment and Key Import*

. Step: Configure the TOE and an external KMS test instance with valid, mutually trusted certificates (or server-only certificates if mutual authentication is not selected).
. Step: Initiate a key import operation.
. Step: Using a network capture tool (e.g., Wireshark), capture traffic between the TOE and KMS.
. Step: Verify the channel uses the TLS protocol version claimed in the ST.

Expected result: The channel is established successfully. The key import completes. Network capture confirms TLS is in use and no plaintext key material is visible in the packet payloads.

---

*Test 2: Rejection of Untrusted KMS Certificate*

. Step: Configure a test KMS instance with a self-signed certificate not present in the TOE's trusted CA store.
. Step: Attempt a key import from the TOE to this untrusted KMS.
. Step: Observe the TOE's behavior and any error messages or audit log entries generated.

Expected result: The TOE rejects the channel establishment. The key import does not proceed. No key material is transmitted. An audit event or error is generated consistent with the TSS description.

---

*Test 3: Mutual Authentication — Client Certificate Required*

Applicable when "Mutual Authentication" is selected in `FDP_ITC_EXT.1.2`.

. Step: Remove or invalidate the TOE's client certificate (or configure the KMS to require client authentication with a different trusted CA than the one that signed the TOE certificate).
. Step: Attempt a key import operation.
. Step: Observe the result and any error messages or audit log entries.

Expected result: The KMS rejects the connection. The key import does not proceed. The TOE logs an appropriate error consistent with the TSS description.

---

*Test 4: Key Material Confidentiality in Transit*

. Step: Using a network capture tool, capture all traffic between the TOE and the KMS during a complete key import operation.
. Step: Examine the captured packets for any plaintext representation of the imported key material.

Expected result: Key material is not found in plaintext in any captured packets. The payload of all post-handshake TLS records is encrypted and not interpretable without the session keys.

---

[appendix]
== Test Environment Requirements

=== General Test Environment

The evaluator shall deploy the TOE in a representative test environment that includes:

. A fully configured DBMS installation per the developer's preparative guidance.
. Access to low-level storage inspection tools (binary editor, hex dump utility, or raw disk access) for data-at-rest tests.
. A network traffic capture capability (e.g., Wireshark, tcpdump) for key import channel tests.
. An external KMS test instance (hardware or software) for BYOK and trusted channel tests.
. Separate operating system accounts with differing privilege levels for access control tests.

=== KMS Test Environment

For evaluations involving FDP_ITC_EXT.1 and FCS_CKM_EXT.1 BYOK paths:

. Deploy a KMS test instance (e.g., HashiCorp Vault development instance, or an equivalent test KMS) accessible from the TOE test environment.
. Provision a valid PKI test hierarchy: a test CA, a KMS server certificate signed by the test CA, and (if mutual authentication is claimed) a TOE client certificate signed by the test CA.
. Configure the KMS with a test MEK or key wrapping key suitable for the import test.
. Configure the TOE's trusted CA store with the test CA certificate.
. Confirm network capture is possible between the TOE and KMS prior to beginning tests.

=== Storage Inspection Prerequisites

For data-at-rest tests (FDP_DAR_EXT.1):

. Identify the physical or logical storage files used by the TOE for data files, redo/transaction logs, undo files, and temporary tablespace.
. Confirm the ability to stop the DBMS service and access raw storage files while the service is stopped.
. Identify and document the location of any keystore files for DEK/MEK storage inspection.

== Test Evidence Requirements

For each test activity, the evaluator shall record:

. Test date and environment configuration (DBMS version, OS version, KMS type/version if applicable).
. Test steps executed.
. Actual results observed.
. Pass/fail determination with rationale.
. Any deviations from documented procedures and justification.

Evidence should include:

. Command output or screenshots demonstrating test execution and results.
. Audit log excerpts showing generated records where applicable.
. Network captures (for FDP_ITC_EXT.1 tests), with session keys excluded.
. Binary/hex excerpts from storage inspection (for FDP_DAR_EXT.1 tests), confirming presence or absence of plaintext.
. Configuration files or system view output used during testing.
